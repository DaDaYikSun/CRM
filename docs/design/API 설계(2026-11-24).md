화면과 서버가 주고받는 약속이다. 작업분배 4장의 계약(C1~C22)을 한곳에 모으고, 경로 · 입력 · 출력 · 오류 · 허용 역할을 정했다.

**표시**
- `[제안]`: 기획 문서와 계약 목록에 없어서 이 초안이 정한 것. 리뷰 때 바꿀 수 있다.
- `[?]`: 문서에 답이 없어 팀이 정해야 하는 것. 7장에 모았다.
- 이슈 번호는 GitHub 번호다. 초안 번호(#01~#35)와의 대응은 작업분배 부록에 있다.

### 1-2. 응답 형식 (C1)

성공:

```json
{ "data": { "petId": 3, "name": "보리" } }
```

목록 (20개씩):

```json
{ "data": { "items": [ ... ], "page": 1, "size": 20, "total": 57 } }
```

실패:

```json
{ "error": { "code": "VALIDATION_FAILED", "message": "아이 이름을(를) 입력해 주세요.", "fields": [ { "field": "pet.name", "message": "아이 이름을(를) 입력해 주세요." } ] } }
```

- 목록도 `data` 안에 넣는다 [제안]. 화면이 응답을 한 가지 모양으로 풀 수 있게 하기 위해서다.
- `fields`는 입력 검사 실패 때만 있다.
- `message`는 정책 정의서 4-2 문구를 그대로 쓴다 (11/25 회의 d5 · d6 문구는 PR #83).

### 1-3. 목록 · 페이지

| 항목 | 규칙 | 근거 |

| 페이지 번호 | `page=1`부터 [제안]. 없으면 1 | |

| 정렬 | API마다 정해진 정렬만 쓴다. 정렬을 바꾸는 입력은 받지 않는다 | POL-TGT-001 |

**다시 시도 규칙 (POL-ERR-001 · 002):** 조회(`GET`) 실패는 화면이 자동으로 한 번 다시 부른다. 저장(`POST` · `PUT` · `PATCH`) 실패는 자동으로 다시 부르지 않는다. 같은 기록이 두 번 생기지 않게 하기 위해서다. 이 규칙은 `lib/api/client.ts`(#13 · #29)가 지킨다.

**저장을 두 번 눌렀을 때 (11/25 회의 R6, POL-ERR-002):** 방문 기록(`POST /api/pets/{id}/visits`), 연락 결과(`POST /api/contacts`, `POST /api/contacts/sms`), 등록(`POST /api/guardians`, `POST /api/guardians/{id}/pets`)은 서버가 같은 요청을 한 번만 저장한다. 화면 버튼 잠금만으로 끝내지 않는다. [?] 같은 요청을 알아보는 방법(요청 키 헤더 등)은 #13에서 정한다.

**같은 전화번호는 오류가 아니다.** 경고만 하고 그래도 새로 등록할 수 있다 (POL-REG-005). 그래서 확인 API(`phone-check`)를 따로 둔다.

### 1-7. 역할 검사

- 역할은 3가지다: `ADMIN`(관리자: 원장 · 데스크 실장), `DESK`(데스크), `GROOMER`(미용사). 원장과 데스크 실장은 같은 `ADMIN`이다 (POL-ACC-001).
- 모든 API는 서버에서 역할을 검사한다. 화면에서 메뉴를 숨기는 것만으로 끝내지 않는다 (NFR-SEC-002, POL-ERR-004).
- `ADMIN`은 `DESK`가 할 수 있는 일을 모두 할 수 있다. 원장도 대시보드를 첫 화면으로 쓴다 (POL-ACC-007).
- `GROOMER`는 팀 결정 T3 · POL-ACC-011의 허용 목록만 쓴다. 거부 목록은 2장 맨 아래에 따로 모았다.

화면 문구: "이미 등록된 보호자입니다: {보호자 이름} (아이 {N}마리)" (정책 4-2). 같은 번호 보호자가 여럿일 수 있어 배열로 준다 (`phone`은 UK가 아님, DB 4-2).

**`POST /api/guardians`**

```json
// 입력
{
  "guardian": { "name": "김보호", "phone": "010-0000-0000", "privacyAgreed": true, "smsAgreed": false },
  "pet": {
    "name": "보리",
    "birthDate": "2023-05-02",
    "approxAge": null,
    "breedId": 1,
    "coatTypeId": 3
  }
}
// 출력 201
{ "data": { "guardianId": 7, "petId": 12 } }
```

- 필수 칸: 아이 이름, 생년월일(또는 대략 나이), 품종, 털 유형, 보호자 전화번호 (POL-REG-001), 보호자 이름 (11/25 회의 d1). 빠지면 `400 VALIDATION_FAILED`.
- `birthDate`와 `approxAge` 중 하나만 받는다. `approxAge`는 `{ "years": 3 }` 또는 1살 미만이면 `{ "months": 5 }`다. 서버가 오늘(한국 시간)에서 빼서 `birth_date`를 만들고 `birth_date_estimated = 1`로 둔다 (POL-REG-004).
- 저장하면 `customer`는 '아이 등록됨' 이벤트만 낸다. `cycle`이 같은 트랜잭션에서 듣고 `createInitialSchedules(petId)`(C4)로 예정 일정을 만든다. `customer`는 `cycle`을 부르지 않는다 (11/25 회의 R3, 4-1).
- 같은 요청을 두 번 받으면 한 번만 저장한다 (R6, 1-5).
- 선택 항목(보조 연락처, 선호 연락 방법, 등록번호, 펫보험, 체중)은 #30이 같은 입력에 더한다.
- 보호자 이름(`guardian.name`)은 필수다 (11/25 회의 d1). 정책 담당이 POL-REG-001 필수 칸에 보호자 이름을 더한다. DB `guardian.name` NOT NULL 그대로다 (6장 2번).

**`POST /api/guardians/{id}/pets`** → 입력은 위의 `pet`과 같다. 출력 `201 { "data": { "petId": 13 } }`.

      "petId": 12, "name": "보리", "species": "DOG", "status": "ACTIVE",

- 확인 모달 문구의 {보류 기간}은 화면이 기준값을 받아 채운다 (정책 4-2, T6). 모달을 열기 전에 `GET /api/options/settings`의 `rainbowHoldDays`로 받는다 (3-2, 7장 10번).

**`POST /api/pets/{petId}/visits`**

```json
// 입력
{ "serviceType": "VACCINE", "vaccineTypeId": 1, "visitDate": "2026-11-24", "memo": null, "broughtByPhone": null }
// 출력 201
{
  "data": {
    "visitId": 501,
    "completedScheduleId": 101,
    "nextSchedule": { "scheduleId": 140, "serviceType": "VACCINE", "vaccineTypeId": 1, "dueDate": "2027-11-24" },
    "groomInterval": null
  }

```

- `serviceType = 'VACCINE'`이면 `vaccineTypeId` 필수, `GROOMING`이면 `null` (DB CHECK).
- `visitDate`가 없으면 오늘 (FR-VIS-002).
- 메모 200자 (POL-DATA-010). `broughtByPhone`은 #39가 더한다. 보호자 정보는 바꾸지 않는다 (POL-REG-006).
- 미용사가 `VACCINE`을 보내면 `403 FORBIDDEN` (T3).
- 무지개다리 아이면 `409 PET_RAINBOW`.
- 저장하면 `visit`은 '방문 기록됨' 이벤트만 낸다. 같은 트랜잭션에서 `cycle`이 듣고 주기를 닫고 다음 주기를 만들며(C4), `contact`가 듣고 전환을 판정한다(C14, FR-CNT-004, DB 5-3). `visit`은 `cycle` · `contact`를 부르지 않는다 (R3, 4-1).
- 출력의 `nextSchedule` · `groomInterval`은 `cycle` 값이라, 저장이 끝난 뒤 조립 자리에서 `cycle` Reader로 읽어 붙인다 (4-1).
- 같은 요청을 두 번 받으면 한 번만 저장한다 (R6, 1-5).
- 미용이면 `groomInterval`에 다시 계산한 개인 주기를 준다: `{ "days": 34, "basis": "MEDIAN" }` (FR-VIS-002).
- [?] 미래 날짜를 막을지.

**`POST /api/contacts`**

```json
// 입력
{
  "guardianId": 7,
  "method": "PHONE",
  "talkedWith": "SELF",
  "memo": "종합백신 누락, 광견병 같이 맞을 예정",
  "nextContactDate": null,
  "items": [ { "scheduleId": 101, "result": "NO_ANSWER" }, { "scheduleId": 102, "result": "NO_ANSWER" } ],
  "applyToHousehold": false
}
// 출력 201
{
  "data": {
    "contactGroupId": "3f1c…",
    "followUp": {
      "closedScheduleIds": [101],
      "mockSms": { "sent": true, "template": "VACCINE" }
    }
  }
}
```

- 결과는 예정 항목마다 하나다. 화면은 기본으로 모두 같은 결과를 채운다 (POL-CNT-002, S7).
- `result`는 5가지만 받는다. `method = 'PHONE'`이면 항목마다 `result` 필수 (DB CHECK).
- `items[].scheduleId`는 이 보호자 아이의 진행 중 주기여야 한다. 아니면 `400`.
- 메모 200자 (POL-DATA-010). 기록한 직원 · 시간은 서버가 붙인다 (POL-CNT-003).
- `nextContactDate`가 없고 결과가 '전화 안 받음'이면 서버가 내일로 채운다 (POL-TGT-006).
- 저장과 같은 트랜잭션에서 `ContactFollowUpService.apply(contactGroupId)`(C14)를 부른다. `schedule.contact_state` · `no_answer_count` · `next_contact_date`는 `contact`가 직접 고치지 않고 `cycle`이 만든 인터페이스로 고친다. `guardian.phone_status`도 `customer`가 만든 인터페이스로 고친다 (C12, R3, 4-1).
- 같은 요청을 두 번 받으면 한 번만 저장한다 (R6, 1-5).
- 2일차 '전화 안 받음'이면 그 주기를 끝내고(`CLOSED`), 수신 동의가 있으면 안내 문자를 모의 발송으로 한 번 기록한다. 접종 · 미용이 섞이면 접종 문구를 쓴다. 동의가 없으면 문자 없이 끝낸다 (POL-TGT-006, T4). 결과는 `followUp`으로 알려 준다.
- `applyToHousehold`(#40): `true`면 같은 집 다른 아이의 진행 중 주기에도 같은 결과를 남긴다. 기본 `false` (POL-CNT-004).
- 저장 성공 문구: "연락 결과를 저장했습니다." (정책 4-2).

### 4-1. 도메인 방향 (11/25 회의 R3)

- 읽기는 아래쪽으로만 한다: `common` ← `auth` ← `customer` ← `visit` ← `cycle` ← `contact` ← `target` ← `dashboard` · `report` · `search` · `admin` 화면.
- 다른 도메인 값은 그 주인이 만든 인터페이스(Reader · 계약)로만 가져온다. 다른 패키지의 Entity · Repository를 import하지 않는다.
- 반대 방향 알림은 이벤트로 한다. 같은 트랜잭션에서 듣는다.

| 이벤트 | 내는 곳 | 듣는 곳 | 하는 일 |
| --- | --- | --- | --- |
| 아이 등록됨 | `customer` (`POST /api/guardians`, `POST /api/guardians/{id}/pets`) | `cycle` | 첫 예정 일정 만들기 (C4) |
| 프로필 바뀜 | `customer` (`PATCH /api/pets/{id}`, `rainbow-revert`) | `cycle` | 아직 오지 않은 예정일 다시 계산 (C4) |
| 방문 기록됨 | `visit` (`POST /api/pets/{id}/visits`) | `cycle`, `contact` | 주기 닫기 · 다음 주기 (C4), 전환 판정 (C14) |

- 여러 도메인을 합치는 화면은 조립 자리에서 합친다. 조립 자리는 합치는 도메인들보다 위층이다 [제안, 위치는 #13에서]. 응답 모양은 3장 그대로다.

| 화면 · API | 합치는 값 | 조립 |
| --- | --- | --- |
| 아이 상세 `GET /api/pets/{id}` | `customer` + `cycle`(`schedules`) | `cycle` 위 조립 자리 |
| 보호자 상세 `GET /api/guardians/{id}` | `customer` + `cycle`(`nextSchedule`) | `cycle` 위 조립 자리 |
| 방문 저장 출력 `nextSchedule` · `groomInterval` | `visit` + `cycle` | 저장 뒤 `cycle` 위 조립 자리 |
| 타임라인 `GET /api/pets/{id}/timeline` | `visit` + `contact` | `contact` 위 조립 자리 |
| 미용 목록 `GET /api/grooming` | `cycle` + 아래 `customer` · `visit` | `cycle`이 Reader로 읽음 |
| 연락 패널 · 연락 대상 | `contact` · `target` + 아래 도메인 | 각자 Reader로 읽음 |

- 목록 · 통계(연락 대상, 대시보드, 검색, 리포트)는 조회 전용 쿼리로 여러 테이블을 바로 읽어도 된다. 단, 주인이 저장한 결과만 읽고 판단을 다시 하지 않는다 (R9, 예: 누락은 `missed_at`만 센다).

### 4-2. admin 패키지 (11/25 회의 R4)

`admin`은 백오피스 화면 · Controller만 둔다. 저장 규칙은 값의 주인 서비스에 있다 (3-10 머리말). `admin` Controller가 주인 서비스를 부르고, 주인 서비스가 `admin`을 읽는 일은 없다.

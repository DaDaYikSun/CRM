### 1-2. 응답 형식 (C1)

성공:

```json
{ "data": { "petId": 3, "name": "보리" } }
```

목록 (20개씩):

```json
{ "data": { "items": [ ... ], "page": 1, "size": 20, "total": 57 } }
```

실패:

```json
{ "error": { "code": "VALIDATION_FAILED", "message": "아이 이름을(를) 입력해 주세요.", "fields": [ { "field": "pet.name", "message": "아이 이름을(를) 입력해 주세요." } ] } }
```

- 목록도 `data` 안에 넣는다 [제안]. 화면이 응답을 한 가지 모양으로 풀 수 있게 하기 위해서다.
- `fields`는 입력 검사 실패 때만 있다.
- `message`는 정책 정의서 4-2 문구를 그대로 쓴다 (11/25 회의 d5 · d6 문구는 PR #83).

### 1-3. 목록 · 페이지

| 항목 | 규칙 | 근거 |
| --- | --- | --- |
| 한 번에 보여주는 수 | 20개 고정. `size`는 받지 않는다 | NFR-PERF-002, 정책 6장 |
| 페이지 번호 | `page=1`부터 [제안]. 없으면 1 | |
| 페이지 상한 | 1보다 작거나 숫자가 아니면 `400 VALIDATION_FAILED`. 마지막 페이지보다 크면 오류 없이 `items: []`와 `total`을 준다. 서버는 `OFFSET`을 `total` 안으로만 계산한다 (`common/web/PageQuery`, #142) | 11/25 회의 R8 |
| 정렬 | API마다 정해진 정렬만 쓴다. 정렬을 바꾸는 입력은 받지 않는다 | POL-TGT-001 |

| 409 | `PET_RAINBOW` | 무지개다리 아이에게 방문 · 연락 기록 | 무지개다리로 표시된 아이라 기록을 남길 수 없습니다. 기록이 필요하면 관리자에게 표시 되돌리기를 요청해 주세요. (d6) 화면은 버튼을 숨긴다 (POL-END-002) |

**다시 시도 규칙 (POL-ERR-001 · 002):** 조회(`GET`) 실패는 화면이 자동으로 한 번 다시 부른다. 저장(`POST` · `PUT` · `PATCH`) 실패는 자동으로 다시 부르지 않는다. 같은 기록이 두 번 생기지 않게 하기 위해서다. 이 규칙은 `lib/api/client.ts`(#142, 재시도 화면은 #168)가 지킨다.

**저장을 두 번 눌렀을 때 (11/25 회의 R6, POL-ERR-002):** 방문 기록(`POST /api/pets/{id}/visits`), 연락 결과(`POST /api/contacts`, `POST /api/contacts/sms`), 등록(`POST /api/guardians`, `POST /api/guardians/{id}/pets`)은 서버가 같은 요청을 한 번만 저장한다. 화면 버튼 잠금만으로 끝내지 않는다. 같은 요청은 헤더 `Idempotency-Key`로 알아본다 (#142, K15): 화면이 폼 하나에 키 하나를 만들어 저장 요청에 싣고, 서버(`common/web/IdempotencyFilter`)는 같은 세션 · 같은 주소 · 같은 키의 요청을 한 번만 처리해 두 번째 요청에 처음 응답을 그대로 준다. 자세한 것은 `backend/README.md` '저장 두 번 막기'.

**보장 범위 (#189):**
- 저장 API는 쓰기를 커밋한 뒤에는 5xx로 답하지 않는다. 서버는 오류 응답(4xx · 5xx)을 기억하지 않아 같은 키로 다시 오면 새로 처리하므로, 커밋 뒤에 5xx를 주면 같은 기록이 두 번 생긴다. 커밋 뒤에 생긴 실패(문자 발송 등)는 성공 응답 안에서 알린다 (3-6 K21 줄). 이 규칙은 필터와 공통 예외 처리가 지켜 주지 않는다: `IdempotencyFilter`는 400 이상이면 키를 지우고, `GlobalExceptionHandler`는 처리하지 못한 예외를 모두 500으로 바꾼다. 그래서 커밋 뒤 예외를 저장 구현이 직접 잡아 성공 응답으로 바꿔야 지켜진다. 각 저장 API 구현 PR에서 이 조건을 확인한다. 저장 메서드 밖에서 나는 응답 변환 실패는 아래 MVP 한계에 적었다.
- 키와 응답은 서버 메모리에 10분(`IdempotencyStore.TTL`) 동안만 있다. 서버가 다시 켜지거나 10분이 지난 뒤 같은 키로 다시 보내면 새 요청으로 처리된다. DB에도 중복을 막는 유일 키가 없다(`visit`, `contact_log.contact_group_id`, `guardian.phone`은 POL-REG-005라 유일하지 않음). 커밋 뒤 응답 본문을 만들다 실패하는 경우(저장 메서드가 값을 돌려준 뒤 JSON 변환 실패, 코드 버그)도 저장 구현이 잡을 수 없어 500이 나가고 키가 풀린다. 그래서 응답 객체는 트랜잭션 안에서 단순 값(DTO)으로 다 만들어 돌려주고(엔티티를 그대로 돌려주지 않음), 각 저장 API 테스트로 응답 변환을 확인한다. 이 한계가 실제로 걸리는 것은 같은 폼에서 같은 키로 다시 보낼 때뿐이다 (화면은 폼 하나에 키 하나, `client.ts`). POL-ERR-002에는 기간 예외가 없으므로, MVP가 이 한계를 받아들이는 것은 [제안]이고 정책 담당(이종민) 승인 전이다. 승인되면 팀 결정 기록에 K 번호로 남긴다. 서버를 여러 대로 늘리거나 실제 문자 발송(v2)을 할 때 키를 DB에 보관할지 다시 정한다.

**같은 전화번호는 오류가 아니다.** 경고만 하고 그래도 새로 등록할 수 있다 (POL-REG-005). 그래서 확인 API(`phone-check`)를 따로 둔다.

### 1-7. 역할 검사

- 역할은 3가지다: `ADMIN`(관리자: 원장 · 데스크 실장), `DESK`(데스크), `GROOMER`(미용사). 원장과 데스크 실장은 같은 `ADMIN`이다 (POL-ACC-001).

**`POST /api/auth/login`**

```json
// 입력
{ "loginId": "desk01", "password": "********" }
// 출력 200
{ "data": { "staffId": 2, "name": "데스크 직원", "role": "DESK", "mustChangePassword": false } }
```

- 실패: `401 LOGIN_FAILED`.
- 화면은 `role`로 첫 화면을 고른다: `ADMIN` · `DESK` → S-02 대시보드, `GROOMER` → S-11 미용 (POL-ACC-007, T2).
- `mustChangePassword = true`면 S-01의 새 비밀번호 화면으로 보낸다.
- 성공하면 `staff.last_login_at`을 채운다.

**`GET /api/auth/me`** → 로그인 출력과 같은 모양. 계약 C3의 출력에 `mustChangePassword`를 더했다 [제안]. 새로고침해도 새 비밀번호 화면을 지키기 위해서다.

**`POST /api/auth/logout`** → 입력 없음, 출력 `200 { "data": null }` (#167).

- 세션을 지운다. 로그인이 없거나 이미 만료된 세션이어도 `200`이다 (로그인 없이 부를 수 있는 주소. CSRF 토큰은 받는다).
- 화면은 페이지를 새로 열어 S-01로 간다. 확인 창은 없다 (POL-ACC-008).

**만료 (1-6, #167)**: 로그인 때 세션에 로그인 시각을 넣고, 요청마다 '로그인 뒤 8시간'을 본다. 지났거나 로그인 시각이 없는 세션은 지우고 `401 SESSION_EXPIRED`. 화면은 `401 SESSION_EXPIRED`를 받으면 `/login?expired=1&next={보던 주소}`로 보내고, 다시 로그인하면 `next`로 돌아온다. `next`는 이 사이트 안의 주소이고 그 역할이 열 수 있을 때만 쓰고, 아니면 역할별 첫 화면. 정규화한 최종 경로(`/a/..//x` → `//x`)도 다시 보고, 제어 문자가 섞이면 받지 않는다 (CWE-601).

**`POST /api/auth/password`**

```json
// 입력
{ "newPassword": "********" }
// 출력 200
{ "data": null }
```

- 규칙에 안 맞으면 `400 PASSWORD_RULE`.
- 성공하면 `must_change_password = 0`.
- [?] 지금 비밀번호도 함께 받을지. #44 계약은 `newPassword`만 받는다.

**`POST /api/pets/{id}/rainbow`**

```json
// 출력 200
{ "data": { "holdUntil": "2026-12-24", "heldPetIds": [13] } }
```

- 아이 `status = 'RAINBOW'`, `rainbow_at = 지금`. 같은 집 다른 아이는 `contact_hold_until = 오늘 + RAINBOW_HOLD_DAYS`, `contact_hold_by_pet_id = 이 아이` (POL-TGT-003, POL-END-003). 이미 다른 아이 때문에 보류 중이면 두 마감(지금 `contact_hold_until`, 오늘 + `RAINBOW_HOLD_DAYS`) 중 늦은 쪽을 남기고, `contact_hold_by_pet_id`는 그 마감을 건 아이로 둔다 [제안]. 관리자가 `RAINBOW_HOLD_DAYS`를 줄이면 새 마감이 더 이를 수 있어서다. 기준값을 줄여도 이미 저장된 보류는 줄이지 않는다 [제안, 7장 17번].
- `change_log`에 `STATUS_CHANGE`로 남긴다. `after_json`에 이 아이 때문에 건 보류 마감 `holdUntil`(오늘 + `RAINBOW_HOLD_DAYS`)을 같이 넣는다. 되돌리기 때 이 값을 쓴다 (스키마 변경 없음, DB 4-14).
- 확인 모달 문구의 {보류 기간}은 화면이 기준값을 받아 채운다 (정책 4-2, T6). 모달을 열기 전에 `GET /api/options/settings`의 `rainbowHoldDays`로 받는다 (3-2, 7장 10번).

**`POST /api/pets/{id}/rainbow-revert`** (관리자) → `status = 'ACTIVE'`, 이 아이 때문에 생긴 같은 집 보류를 푼다. 같은 집에 아직 무지개다리인 다른 아이가 있고 그 아이의 저장된 보류 마감 `holdUntil`이 오늘이거나 그 뒤면(`holdUntil >= :today`) 보류를 풀지 않고, 그런 아이 중 `holdUntil`이 가장 늦은 아이의 날짜 · `contact_hold_by_pet_id`로 바꾼다 [제안]. `contact_hold_by_pet_id`는 한 칸이라, 두 아이가 겹쳐 보류를 건 뒤 한 아이를 되돌려도 남은 보류가 풀리지 않게 하려는 것이다. `holdUntil`은 그 아이의 `change_log` 중 `status`를 `RAINBOW`로 바꾼 `STATUS_CHANGE` 행 가운데 가장 최근 것의 `after_json.holdUntil`이다. 되돌리기 행에는 `holdUntil`을 넣지 않고 이 조회에서도 뺀다. 남은 아이를 고를 때도, 바꿀 마감도 지금 기준값으로 다시 계산하지 않고 이 `holdUntil`만 쓴다. `holdUntil`이 오늘보다 앞이면 그 아이의 보류는 이미 끝난 것으로 본다. 연락 대상 목록은 `contact_hold_until`이 오늘보다 앞일 때만 다시 넣으므로(DB 5-2), 마감 당일까지 보류가 유지된다. 그래서 '기준값을 줄여도 저장된 보류는 줄이지 않는다'는 표시 때 원칙과 같다 (7장 17번). 보류가 남는 경우 되돌리기 확인 문구(정책 4-2 '같은 집 연락 보류가 풀립니다')가 맞지 않는 점은 정책 담당이 본다. '프로필 바뀜' 이벤트를 내면 `cycle`이 듣고 `recalculatePet`으로 빠졌던 기간을 소급 계산한다 (POL-END-004, R3). 출력 `{ "data": { "releasedPetIds": [13] } }`.

- `serviceType = 'VACCINE'`이면 `vaccineTypeId` 필수, `GROOMING`이면 `null` (DB CHECK).
- `visitDate`가 없으면 오늘 (FR-VIS-002).

- 저장하면 `visit`은 '방문 기록됨' 이벤트만 낸다. 같은 트랜잭션에서 `cycle`이 듣고 주기를 닫고 다음 주기를 만들며(C4), `contact`가 듣고 전환을 판정한다(C14, FR-CNT-004, DB 5-3). 전환 판정은 `cycle`이 닫은 주기가 필요하므로 `cycle`이 먼저 듣는다 (리스너 순서 `cycle` → `contact`) [제안]. `visit`은 `cycle` · `contact`를 부르지 않는다 (R3, 4-1).
- 출력의 `nextSchedule` · `groomInterval`은 `cycle` 값이라, 저장이 끝난 뒤 조립 자리에서 `cycle` Reader로 읽어 붙인다 (4-1).
- 같은 요청을 두 번 받으면 한 번만 저장한다 (R6, 1-5).
- 미용이면 `groomInterval`에 다시 계산한 개인 주기를 준다: `{ "days": 34, "basis": "MEDIAN" }` (FR-VIS-002).
- 오늘(한국 시간) 뒤 `visitDate`는 `400 VALIDATION_FAILED` (`visitDate`) (요구사항 근거 없음(설계 결정), #148, 7장 14번). 아이 생년월일보다 이른 날도 같다: 접종 예정일 계산이 500으로 끝나던 경우를 막는다 (요구사항 근거 없음(설계 결정), #148 · PR #220 리뷰).
- 같은 아이 · 같은 날 · 같은 서비스(접종이면 같은 종류)가 이미 있으면 `400 VALIDATION_FAILED` (`visitDate`). 같은 날 다른 종류는 저장된다 (요구사항 근거 없음(설계 결정), #148. 두 번 누름 K15와는 다른 경우).

- 방문 줄은 `visit`, 연락 줄은 `contact` 것이다. `visit`이 `contact`를 읽으면 방향이 거꾸로라, 조립 자리에서 두 주인의 Reader로 합쳐 날짜순으로 줄 세운다 (R3, 4-1). 조회 전용 쿼리로 바로 읽어도 된다 (R9).
- [?] 누락 접종의 빨간 표시를 타임라인 줄로 넣을지, `GET /api/pets/{id}`의 `schedules[].missed`로만 보여줄지 (FR-VIS-003).

**`POST /api/contacts`**

```json
// 입력
{
  "guardianId": 7,
  "method": "PHONE",
  "talkedWith": "SELF",
  "memo": "종합백신 누락, 광견병 같이 맞을 예정",
  "nextContactDate": null,
  "items": [ { "scheduleId": 101, "result": "NO_ANSWER" }, { "scheduleId": 102, "result": "NO_ANSWER" } ],
  "applyToHousehold": false
}
// 출력 201
{
  "data": {
    "contactGroupId": "3f1c…",
    "followUp": {
      "closedScheduleIds": [101],
      "mockSms": { "sent": true, "template": "VACCINE" }
    }
  }
}
```

- 결과는 예정 항목마다 하나다. 화면은 기본으로 모두 같은 결과를 채운다 (POL-CNT-002, S7).
- `result`는 5가지만 받는다. `method = 'PHONE'`이면 항목마다 `result` 필수 (DB CHECK).
- `items[].scheduleId`는 이 보호자 아이의 진행 중 주기여야 한다. 아니면 `400 VALIDATION_FAILED`.
- 메모 200자 (POL-DATA-010). 기록한 직원 · 시간은 서버가 붙인다 (POL-CNT-003).
- `nextContactDate`가 없고 결과가 '전화 안 받음'이면 서버가 내일로 채운다 (POL-TGT-006).
- 저장과 같은 트랜잭션에서 `ContactFollowUpService.apply(contactGroupId)`(C14)를 부른다. `schedule.contact_state` · `no_answer_count` · `next_contact_date`는 `contact`가 직접 고치지 않고 `cycle`이 만든 인터페이스로 고친다. `guardian.phone_status`도 `customer`가 만든 인터페이스로 고친다 (C12, R3, 4-1).
- 같은 요청을 두 번 받으면 한 번만 저장한다 (R6, 1-5).
- 2일차 '전화 안 받음'이면 그 주기를 끝내고(`CLOSED`), 수신 동의가 있으면 안내 문자를 모의 발송으로 한 번 기록한다. 접종 · 미용이 섞이면 접종 문구를 쓴다. 동의가 없으면 문자 없이 끝낸다 (POL-TGT-006, T4). 결과는 `followUp`으로 알려 준다.
- 2일차 문자와 트랜잭션 (K21): 연락 결과와 모의 발송 기록(`contact_log` INSERT)은 같은 트랜잭션에 저장한다. `SmsSender` 호출만 트랜잭션 밖(커밋 뒤)에서 한다. `SmsSender`가 실패해도 연락 결과는 되돌리지 않고, 화면은 '2일차 마침' 토스트 대신 정책 4-2 '문자 발송 실패 (2일차)'를 띄운다 (주기가 `CLOSED`라 다시 보낼 곳이 없음). `SmsSender` 실패는 커밋 뒤에 생기므로 5xx가 아니라 성공 응답 안에서 알린다 (1-5 '보장 범위', #189). 모의 발송 기록 저장이 실패하면 트랜잭션 전체가 되돌아가므로 일반 '저장 실패'다 (커밋 전이라 오류 응답). MVP는 모의 발송이라 `SmsSender`가 실패하는 경우가 없고, 실패를 응답에 싣는 모양과 기록 · 발송 순서는 실제 발송(v2)에서 바꿀 수 있다.
- 커밋 뒤 호출은 트랜잭션이 없는 `ContactSmsDispatcher`가 한다: 저장(트랜잭션)이 끝난 뒤 `SmsSender`를 부르고 응답을 만든다. 실패하면 `followUp.mockSms.sent = false`. 같은 키로 다시 받으면 `IdempotencyFilter`가 처음 응답을 돌려줘 기록 · 발송을 다시 하지 않는다 (#154). 이 보장은 10분 안, 서버가 다시 켜지기 전까지만이고 그 뒤에는 새 요청으로 처리된다. MVP가 이 한계를 받아들이는 것은 POL-ERR-002 승인 전 [제안]이다 (1-5 '보장 범위').
- 2일차 안내 문자는 보호자에게 한 통이고 `contact_log` 문자 행도 하나다. 행은 문구를 채운 항목(접종이 있으면 예정일이 가장 이른 접종, 예정일이 같으면 주요 접종, 없으면 미용)에 붙인다. 항목마다 행을 만들면 방법별 전환율에서 한 통이 여러 건으로 세어지기 때문이다 (#154, #174 결정. 고르기 규칙은 아래 `POST /api/contacts/sms`와 같다).
- `applyToHousehold`(#179): `true`면 같은 집 다른 아이의 진행 중 주기에도 같은 결과를 남긴다. 기본 `false` (POL-CNT-004).
- 저장 성공 문구: "연락 결과를 저장했습니다." (정책 4-2).

**`POST /api/contacts/sms/preview`** [제안] (#180)

{ "data": { "body": "[우리동물병원] 보리의 종합백신 접종 예정일은 2026-11-14입니다. 방문 전 0000000000로 예약해 주세요.", "template": "VACCINE" } }

`MessageRenderer.render`(C18)가 채운 문구를 그대로 보여주기 위해 더했다. 실제로 남길 `sms_body`와 미리보기가 같아야 해서 서버에서 채운다. 입력은 발송(`POST /api/contacts/sms`)과 같은 `{ guardianId, items }`이고 `template`은 받지 않는다. 문구 종류는 발송과 같은 고르기 규칙으로 서버가 정하고 출력 `template`으로 알려 준다(화면의 '접종 안내 / 미용 안내' 표시용). 그래서 직원이 본 문구와 기록되는 `sms_body`가 항목 구성과 상관없이 같다. 근거: FR-CNT-007, 요구사항 근거 없음(설계 결정, #174 · #180, PR #253 리뷰). 단문 · 장문 표시는 화면이 글자 수로 계산한다 (DB 4-12).

**`POST /api/contacts/sms`** (#174)

```json
// 입력
{ "guardianId": 7, "items": [ { "scheduleId": 101 } ] }
// 출력 201
{ "data": { "contactGroupId": "9a2e…", "body": "…", "template": "VACCINE", "sent": true } }
```

- 실제로 보내지 않는다. `method = 'SMS'`, `is_mock_sms = 1`, `sms_template`, `sms_body`(채운 원문)로 기록한다 (POL-CNT-005, DB 4-11).
- 패널 항목이 여러 개여도 보호자에게 한 통이고 `contact_log` 문자 행도 하나다. 행은 문구를 채운 항목에 붙인다. 항목마다 행을 만들면 방법별 전환율(FR-DASH-003)에서 한 통이 여러 건으로 세어지기 때문이다 (2일차 문자와 같음). 근거: 요구사항 근거 없음(설계 결정, #174).
- 문구 종류는 서버가 정한다. 입력에 `template`을 보내도 무시한다. 접종 항목이 있으면 예정일이 가장 이른 접종, 없으면 미용 (T4). 예정일이 같은 접종이 여럿이면 주요 접종(`vaccine_type.is_major = 1`)을 먼저 고른다. 2일차 문자도 같은 규칙이다. 근거: T4(접종 · 미용이 섞이면 접종), '예정일이 같으면 주요 접종'은 요구사항 근거 없음(설계 결정, #174).
- 결과 유형(`result`)은 남기지 않는다(NULL). 그래서 주기의 연락 상태 · 전화 안 받음 횟수 같은 후속 처리(C14)를 바꾸지 않고, 연락 효과 지표에서는 방법별 '문자'에만 들어간다. 근거: 요구사항 근거 없음(설계 결정, #174 · #240), 지표는 FR-DASH-003.
- 항목이 이 보호자 아이의 진행 중 예정이 아니면 `400 VALIDATION_FAILED`, 무지개다리 아이면 `409 PET_RAINBOW` (POL-END-002: 무지개다리 아이는 연락 대상에서 뺀다).
- 수신 동의가 없으면 `409 SMS_NOT_AGREED` (POL-REG-010).
- 21시~다음 날 8시 경고는 화면이 보내기 전에 띄운다. 서버는 막지 않는다 (POL-CNT-007).
- 성공 문구: "문자를 보낸 것으로 기록했습니다 (모의 발송)." (정책 4-2).
- 발송 부분은 `SmsSender.send`(C14)로 분리해 나중에 실제 문자 서비스로 바꿀 수 있게 한다 (NFR-EXT-001).
- 트랜잭션 (K21): 모의 발송 기록을 저장한 뒤 `SmsSender`를 트랜잭션 밖에서 부른다. `SmsSender`만 실패하면 기록은 되돌리지 않고 화면은 정책 4-2 '문자 발송 실패'를 띄워 [문자 보내기]로 다시 시도하게 한다. 이때도 커밋 뒤라 5xx가 아니라 성공 응답 안에서 알린다 (1-5 '보장 범위'). 기록 저장이 실패하면 '저장 실패'다. MVP는 실패 경우가 없다 (위 `POST /api/contacts`의 K21 줄).
- `SmsSender`만 실패하면 성공 응답(201)의 `sent = false`로 알린다. 기록은 이미 커밋돼 있어서 [문자 보내기]로 다시 누르면 새 기록이 된다 (2일차 `followUp.mockSms.sent`와 같은 방식, K21, #174).

**`PATCH /api/contacts/{id}`** (#178) → 방문 기록 수정과 같은 규칙. `contact_log.is_edited = 1`, `change_log`에 `RECORD_EDIT`.

- 고칠 수 있는 칸은 `memo`, `talkedWith`, `nextContactDate` 셋이다 [제안]. 결과 유형 · 연락 방법은 `schedule.contact_state` · `no_answer_count`, 후속 처리, 연락 효과 지표와 이어져 있어 고치지 않는다 (7장 4번). 다른 칸을 보내면 `400 VALIDATION_FAILED`.
- `nextContactDate`를 고치면 같은 트랜잭션에서 그 예정 항목의 `schedule.next_contact_date`도 `cycle` 인터페이스로 고친다 (DB 4-10, C12, R3).

**`GET /api/dashboard/metrics?from=2026-11-01&to=2026-11-30`**

```json
{
  "data": {
    "from": "2026-11-01", "to": "2026-11-30",
    "revisitRate": {
      "vaccine":  { "rate": 0.62, "numerator": 31, "denominator": 50 },
      "grooming": { "rate": 0.71, "numerator": 22, "denominator": 31 }
    },
    "vaccineMissRate": { "rate": 0.38, "numerator": 19, "denominator": 50 },
    "avgGapDays": { "vaccine": 6.4, "grooming": -1.2 },
    "conversionByResult": {
      "BOOKED": { "rate": 0.8, "converted": 16, "total": 20 },
      "NO_ANSWER": { "rate": 0.2, "converted": 3, "total": 15 },
      "REFUSED": { "rate": 0.0, "converted": 0, "total": 4 },
      "OTHER_HOSPITAL": { "rate": 0.0, "converted": 0, "total": 2 },
      "WRONG_NUMBER": { "rate": 0.0, "converted": 0, "total": 1 }
    },
    "conversionByMethod": {
      "PHONE": { "rate": 0.45, "converted": 19, "total": 42 },
      "SMS":   { "rate": 0.3,  "converted": 3,  "total": 10 }
    }
  }

```

- 계산식은 정책 POL-MISS-003 · 004와 11/25 회의 R9를 따른다. 저장된 누락 판정(`schedule.missed_at`)만 읽고 날짜로 다시 계산하지 않는다.
  - 대상: 서비스(접종 · 미용)별로, 기간 안에 `due_date`가 있는 주기 중 VOID가 아니고, ACTIVE 아이이고, 결과가 정해진 것(`status = 'DONE'` 또는 `missed_at IS NOT NULL`). 아이 기준으로 센다 (`pet_id` 중복 제거). 무지개다리 아이는 뺀다 (POL-MISS-008).
  - 접종은 재방문율 · 누락률 모두 주요 접종(`vaccine_type.is_major = 1`)만 넣는다. 심장사상충 · 구충은 뺀다 (S12).
  - 아이마다 결과를 하나로 정한다: 그 아이의 대상 주기 중 하나라도 `missed_at`이 있으면 누락, 모두 없으면 재방문 (팀 결정 T15, #116, DB 설계 5-4와 같음). 재방문율 = 재방문 아이 수 / 대상 아이 수, 접종 누락률 = 누락 아이 수 / 같은 대상 아이 수. 그래서 한 기간에 완료와 누락이 같이 있는 아이도 한 번만 센다.
  - 서비스마다 재방문율 + 누락률 = 100%다. 응답에 미용 누락 비율 칸은 두지 않는다. 미용 누락 비율 = 100% − `revisitRate.grooming` (위 예: 1 − 0.71 = 0.29, 9/31).
- `avgGapDays`(예정일 대비 실제 방문 차이, 일): 서비스별 평균, 소수 첫째 자리. 대상은 재방문율과 같은 주기 중 완료(`DONE`)된 것이고, 늦게 완료된 주기도 넣는다. 완료 주기가 없으면 `null`. 근거: FR-DASH-002. 서비스별로 나누는 것 · 대상은 요구사항 근거 없음(설계 결정, #157, DB 설계 5-4와 같음).
- 전환율(`conversionByResult` · `conversionByMethod`): 기간 안에 연락한 연락(`contacted_at`, 한국 날짜 양 끝 포함)을 센다. ACTIVE 아이만. 결과 유형별은 결과가 있는 행만, 방법별은 모든 행(2일차 뒤 보낸 안내 문자도 문자, 정책 4-4). 결과 5가지 · 방법 2가지 칸은 0건이어도 둔다. 근거: FR-DASH-003, POL-MISS-008. 연락한 날 기준 · 0건 칸 유지는 요구사항 근거 없음(설계 결정, #157, DB 설계 5-4와 같음).
- `rate`와 함께 분자 · 분모를 준다 [제안]. 확인 방법이 "엑셀로 손계산한 값과 같다"라서, 화면이나 리뷰에서 바로 대조할 수 있게 하기 위해서다.
- 분모가 0이면 `rate = null`. 화면은 '아직 기록이 없습니다'를 보여준다 (POL-ERR-008).
- 기간 선택지(이번 달 / 지난 3개월 / 직접 선택)는 화면이 `from` · `to`로 바꿔 보낸다 (FR-DASH-005). `from` · `to`가 없으면 이번 달(한국 시간)로 센다. 근거: FR-DASH-005, 요구사항 근거 없음(설계 결정, #157). 화면 설계 S-02 '상태' 항목의 '처음: 기간 이번 달'과 같다. 하나만 오면 빠진 쪽을 같은 달의 처음 · 끝으로 채운다 (요구사항 근거 없음, 설계 결정, #157). 형식이 틀리거나 `from > to`면 `400 VALIDATION_FAILED`. 오늘(한국 날짜)보다 뒤는 세지 않는다: `to`가 오늘 뒤면 오늘로 자르고(이번 달 기본값도 1일 ~ 오늘), `from`이 오늘 뒤면 `400 VALIDATION_FAILED` (`from`). '지난 3개월'은 이번 달을 넣어 두 달 전 1일 ~ 오늘이다. 화면은 직접 선택에서 오늘 뒤를 고르지 못하게 한다. 근거: FR-DASH-005, 요구사항 근거 없음(설계 결정, #176).
- CRM 도입 전 · 후 비교(FR-DATA-002)는 대시보드 기능이 아니다. 같은 API를 `CRM_START_DATE` 앞 · 뒤 기간으로 두 번 불러 발표 자료를 만든다.

- 직원 추가 때 서버가 임시 비밀번호를 만들어 한 번만 돌려주고 `must_change_password = 1`로 둔다. 정책 4-4 B-01 문구("추가하면 임시 비밀번호가 한 번 보입니다")를 따른 것이다. 계약 C16은 입력에 `password`를 받았는데, 정책을 우선했다 (6장 3번).
- 직원 목록은 몇 명뿐이라 페이지로 나누지 않는다 [제안].
- 비활성화해도 기록의 `created_by`는 그대로다 (POL-ACC-004). 비활성 직원은 로그인할 수 없다.
- 비활성화하면 그 직원의 세션을 모두 지운다. 다른 PC에 로그인해 둔 것도 바로 끊긴다 (11/25 회의 R5, POL-ACC-004, 1-6).
- 역할을 바꿔도 그 직원의 세션을 모두 지운다. 세션에 남은 옛 역할로 계속 쓰지 못하게 하기 위해서다 [제안, #150].
- 다시 사용: `{ "isActive": true }`를 받으면 비활성을 풀고 `deactivatedAt`을 지운다 [제안, #150]. 화면에는 아직 버튼을 두지 않았다.
- [?] 관리자가 자기 계정을 비활성화하거나 역할을 내리는 것을 서버에서 막을지 (7장 12번). #150은 화면에서 자기 줄의 [비활성화] · 역할 선택을 숨기기만 한다.
- `reset-password` 출력: `{ "data": { "tempPassword": "********" } }`. 한 번만 보여준다 (POL-ACC-010). 초기화하면 그 직원의 세션을 모두 지운다 (R5, POL-ACC-010).

**누락 판정 (11/25 회의 R1, K3를 바꿈 · 시점은 K20):** 판정할 때 `schedule.missed_at`에 원래 판정일 `DATE_ADD(due_date, INTERVAL miss_threshold_days + 1 DAY)`(`DATE`)를 저장한다. 판정 작업이 제때 돌면 한국 시간 `:today`와 같다. 그래서 누락 기준을 나중에 바꿔도 지난 누락 판정 · 통계는 그대로다 (POL-CYC-005). 판정은 매일 0시(한국 시간) 한 번 도는 판정 작업(`@Scheduled`)이 한다 (팀 결정 K20): 진행 중(`OPEN`)이고 `missed_at`이 비었고 '예정일 + 그 주기의 누락 기준 < 오늘'인 주기에 `missed_at`을 채운다. 목록 · 지표 조회는 `missed_at`만 읽고 다시 계산하지 않는다 (R9). 방문 저장으로 주기를 완료할 때 `missed_at`이 비었는데 기준을 넘겨 왔으면 그때도 채운다. 값은 완료한 날이 아니라 같은 원래 판정일이다 (판정 작업을 건너뛴 날 대비, DB 4-10). 반대로 방문 날짜가 기준 안인데 입력만 판정 뒤라 `missed_at`이 이미 있으면, 완료할 때 `missed_at`을 지운다 (정책 담당 결정 #109, PR #110). 판정 시점은 팀 결정 K20으로 정했다 (PR #138, DB 설계 4-10).

### 4-1. 도메인 방향 (11/25 회의 R3)

- 읽기는 아래쪽으로만 한다: `common` ← `auth` ← `customer` ← `visit` ← `cycle` ← `contact` ← `target` ← `dashboard` · `report` · `search` · `admin` 화면.
- 다른 도메인 값은 그 주인이 만든 인터페이스(Reader · 계약)로만 가져온다. 다른 패키지의 Entity · Repository를 import하지 않는다.
- 반대 방향 알림은 이벤트로 한다. 같은 트랜잭션에서 듣는다.

| 이벤트 | 내는 곳 | 듣는 곳 | 하는 일 |
| --- | --- | --- | --- |
| 아이 등록됨 | `customer` (`POST /api/guardians`, `POST /api/guardians/{id}/pets`) | `cycle` | 첫 예정 일정 만들기 (C4) |
| 프로필 바뀜 | `customer` (`PATCH /api/pets/{id}`, `rainbow-revert`) | `cycle` | 아직 오지 않은 예정일 다시 계산 (C4) |
| 방문 기록됨 | `visit` (`POST /api/pets/{id}/visits`) | `cycle`, `contact` | 주기 닫기 · 다음 주기 (C4), 전환 판정 (C14) |

- 여러 도메인을 합치는 화면은 조립 자리에서 합친다. 조립 자리는 합치는 도메인들보다 위층이다. 위치는 `com.dadayiksun.crm.view` 패키지 [제안, #142] (`backend/README.md` '조립 자리'). 응답 모양은 3장 그대로다.

| 화면 · API | 합치는 값 | 조립 |
| --- | --- | --- |
| 아이 상세 `GET /api/pets/{id}` | `customer` + `cycle`(`schedules`) | `cycle` 위 조립 자리 |
| 보호자 상세 `GET /api/guardians/{id}` | `customer` + `cycle`(`nextSchedule`) | `cycle` 위 조립 자리 |
| 방문 저장 출력 `nextSchedule` · `groomInterval` | `visit` + `cycle` | 저장 뒤 `cycle` 위 조립 자리 |
| 타임라인 `GET /api/pets/{id}/timeline` | `visit` + `contact` | `contact` 위 조립 자리 |
| 미용 목록 `GET /api/grooming` | `cycle` + 아래 `customer` · `visit` | `cycle`이 Reader로 읽음 |
| 연락 패널 · 연락 대상 | `contact` · `target` + 아래 도메인 | 각자 Reader로 읽음 |

- 목록 · 통계(연락 대상, 대시보드, 검색, 리포트)는 조회 전용 쿼리로 여러 테이블을 바로 읽어도 된다. 단, 주인이 저장한 결과만 읽고 판단을 다시 하지 않는다 (R9, 예: 누락은 `missed_at`만 센다).

### 4-2. admin 패키지 (11/25 회의 R4)

`admin`은 백오피스 화면 · Controller만 둔다. 저장 규칙은 값의 주인 서비스에 있다 (3-10 머리말). `admin` Controller가 주인 서비스를 부르고, 주인 서비스가 `admin`을 읽는 일은 없다.

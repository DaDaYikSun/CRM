# 시연용 더미 데이터 (#147)

local · demo 프로필에서만 적재한다 (K8). 운영 DB에는 넣지 않는다.

## 만들기 · 점검

```bash
node backend/scripts/dummy/generate-dummy.mjs   # CSV 6개를 이 폴더에 다시 만든다 (시드 고정, 매번 같은 결과)
node backend/scripts/dummy/check-dummy.mjs      # 더미 데이터 작성 매뉴얼 5장 점검표 확인 (틀리면 종료 코드 1)
```

CSV는 손으로 고치지 않는다. 값을 바꾸려면 생성 스크립트를 고치고 다시 만든다.

## 기간

- 기록 기간: 2025-06-01 ~ 2026-11-25 (기간 직전 기준 접종은 2024-07-01부터)
- 등록 전 과거 기록: 등록할 때 옮겨 적은 접종 이력(종합백신 기초 5회 · 등록 전 1년 안 추가접종, 광견병 1회)은 2024-07-01 전이어도 된다. 예정일 계산이 기초접종을 다 채운 것으로 보게 하려는 것이다 (K24). 등록 뒤 기록은 2024-07-01부터다.
- CRM 도입일: 2026-06-01. 도입 전에는 연락 기록이 거의 없고 누락이 많다. 도입 뒤에는 연락 기록이 쌓이고 누락이 준다.
- 미래 날짜 기록은 없다.

## 파일과 참조 규칙

| 파일 | 행 | 참조 |
| --- | --- | --- |
| `staff.csv` | 직원 5명 | `login_id`로 참조한다. 비밀번호는 없다. 적재기가 시연용 비밀번호를 넣는다. |
| `owners.csv` | 보호자 | `guardian_id`는 CSV 안에서만 쓰는 번호(1부터)다. DB id와 같다고 보지 않는다. |
| `pets.csv` | 반려견 | `breed_name`(품종 이름)과 `coat_type_code`로 기본 데이터를 찾는다. |
| `vaccinations.csv` | 접종 · 예방 방문 | `vaccine_type_code`로 접종 종류를 찾는다. |
| `groomings.csv` | 미용 방문 | |
| `contacts.csv` | 연락 기록 | `schedule_id` · `is_converted` 칸은 없다 (아래 참고). |

- 모든 표의 `created_by_login_id`는 `staff.csv`의 `login_id`다.
- 참/거짓은 `1` / `0`, 빈 값은 빈 칸이다. 날짜는 `YYYY-MM-DD`, 일시는 `YYYY-MM-DD HH:MM:SS`(KST).
- 전화번호는 `0100xxxxxxx` 형식이며 010-0000-0000 ~ 010-0999-9999 범위만 쓴다 (POL-DATA-001).

## 넣기 (적재기, `com.dadayiksun.crm.data.DummyDataLoader`)

1. `backend/.env`에 `DB_*`와 `DUMMY_STAFF_PASSWORD`(더미 직원 5명이 같이 쓰는 비밀번호)를 채운다.
2. local 프로필로 켠다: `cd backend && ./gradlew bootRun --args='--spring.profiles.active=local'`
3. 보호자가 한 명도 없을 때만 넣는다. 다시 켜도 두 번 들어가지 않는다. 처음부터 다시 넣으려면 DB를 비운다.
4. 운영(프로필 없음)에서는 적재기가 없다 (K8).

지금 넣는 것: 직원 · 보호자 · 반려견 · 방문(접종 · 미용) · 예정 일정 · 누락 판정 · 연락 기록 · 주기 연락 상태 · 전환(`is_converted`).

1단계(방문까지)로 넣은 DB에는 2단계가 붙지 않는다 (보호자가 있으면 건너뜀). DB의 테이블을 모두 지우고 다시 켜면 V1부터 다시 만들고 처음부터 넣는다. 2분쯤 걸린다.

## 적재기가 할 일

1. 직원 → 보호자 → 반려견 → 접종 · 미용 기록 순서로 넣는다. `guardian_id` · `pet_id`는 CSV 안 번호라, 넣을 때 DB가 준 id를 CSV 번호별로 기록해 두고 반려견 · 기록 · 연락의 참조를 그 id로 바꿔 넣는다. local · demo DB가 비어 있다고 가정하지 않는다 (이미 보호자가 있거나 자동 증가 번호가 진행됐을 수 있음).
2. 예정 일정은 적재기가 따로 계산하지 않고 cycle 주인 경로를 부른다. 아이마다 등록 전 과거 기록을 넣고 첫 예정 일정, 그 뒤 방문 · 연락을 시간 순서로: 방문은 넣고 '방문 기록됨', 연락은 3. 무지개다리 아이는 기록을 다 넣은 뒤 상태를 바꾸고 다시 계산한다. 끝에 누락 판정 작업을 한 번 돌린다 (`missed_at` = 원래 판정일, K20).
3. 연락 기록은 `pet_id` · `service_type` · `vaccine_type_code`와 연락 시각으로 그때 열린 예정 일정을 찾아 `schedule_id`를 붙인다. 붙일 예정 일정이 없는 연락(등록 전 연락, 규칙 행이 아직 없는 선택 접종)은 넣지 않고 로그에 수를 남긴다.
4. 연락 묶음을 다 넣으면 결과별 후속 처리(C14 `ContactFollowUpService.apply`)를 부른다: 주기 연락 상태 · 전화 안 받음 횟수 · 다음 연락 예정일, 2일차 마침과 모의 발송 문자, 번호 오류. 방문은 '방문 기록됨' 이벤트를 내서 cycle(주기 완료) 다음 contact가 전환(`is_converted`)을 판정한다 (#154). 모두 연락한 시각 · 방문일 기준이라 적재일과 상관없다. 같은 집 묶음 연락이 아이 둘에 걸치므로 등록 뒤 기록은 모든 아이를 한 줄로 시간 순서대로 넣는다.

## 누락률 (생성 스크립트 = 적재 뒤 SQL)

생성 스크립트는 앱과 같은 예정일 계산 규칙(접종 규칙은 마이그레이션의 `vaccine_rule` 행, 미용은 개인 주기 중앙값)으로 주기를 돌고, 마지막에 기대 누락률을 출력한다. 세는 법은 POL-MISS-003 · 004 · T15(서비스별, 기간 안에 예정일이 된 주기 중 결과가 정해진 것, 아이 기준, 주요 접종만, 무지개다리 아이 뺌).

| 서비스 | 도입 전 (2025-06-01 ~ 2026-05-31) | 도입 뒤 (2026-06-01 ~ 2026-11-25) |
| --- | --- | --- |
| 접종 (종합백신 · 광견병) | 29.2% (80 / 274) | 19.6% (53 / 271) |
| 미용 (모든 아이) | 53.5% (116 / 217) | 36% (86 / 239) |
| 미용 (다니는 아이만, 참고) | 34.4% (53 / 154) | 19.6% (37 / 189) |

적재 뒤 SQL 집계도 같다 (SQL 측정일 2026-11-27, 판정 기준일 2026-11-27 = 적재 때 판정 작업이 돈 날. 생성 스크립트 기대값의 판정 기준일은 END 다음 날 2026-11-26). 판정 작업은 그날 한국 날짜로 판정하므로 다른 날 적재하면 도입 뒤 숫자가 조금 달라진다. 미용은 모든 아이에게 첫 미용 예정이 생기므로(DB 설계 5-1) 미용을 안 하는 아이의 첫 예정이 누락으로 잡혀 '모든 아이' 값이 높다.

## 연락 결과별 전환 (도입 뒤 연락, 적재 뒤 SQL)

생성 스크립트도 같은 규칙으로 기대 전환율을 출력한다. 씨앗(`SEED`)은 누락률 · 결과별 전환 · 연락 건수 목표를 모두 만족하는 값으로 골랐다 (`DUMMY_SEED`로 바꿔 볼 수 있다).

전환 판정(#154)은 '연락 뒤 기준 안에 온 방문'을 마지막 연락의 전환으로 센다. 그래서 거절 · 다른 병원 · 번호 오류인데 재방문으로 이어지지 않은 아이는 그 주기에 기준 안에 오지 않게 만든다 (매뉴얼 3-3).

| 결과 | 연락 | 전환 | 매뉴얼 3-3 |
| --- | --- | --- | --- |
| 예약함 (전화 · 문자) | 194 · 64 | 88.7% · 87.5% | 80~90% |
| 거절 | 63 | 6.3% | 5~10% |
| 다른 병원 다님 | 42 | 0% | 0~5% |
| 번호 오류 | 22 | 0% | 0% |
| 전화 안 받음 (1일차 전화 행) | 180 | 8.3% | 다시 연락(2일차 · 문자) 행이 전환을 가져간다 |

## 확인할 것

- `pets.csv`의 품종 이름은 V2 기본 데이터(`V2__seed_base.sql` 품종 표, #142)에 있는 이름만 쓴다. 점검 스크립트가 확인한다.
- 적재기 위치(Java `CommandLineRunner` 또는 SQL)는 #142 뒤에 정한다.
